- **An internal panic while analyzing one file no longer aborts `steins check`: that file reports `internal.panic`, every other file is analyzed as usual, and the run exits `2`.** The finding names the file and the panic, sits at its line 1, and replaces the findings of that file's own walk for the run (project-wide findings, such as `throw.undeclared`, can still appear in it). It is a mechanics-layer id outside every channel: profiles, `@steins-ignore`, the vendor filter and the baseline all pass it through. Exit `2` now also means "Steins itself failed", and wins over `1`; the report is still printed in every format. Nothing writes from a panicked run: `--set-baseline` and `check --fix` refuse, and `transform --apply` and MCP `apply_plan` fail their post-check by name, all exiting `2`. `annotate` exits `2` when its margin shows `✗ internal.panic`. A panicked file's own `@steins-ignore` comments are not reported as `suppress.unmatched`, and its baseline entries are not counted stale. A run that reports one publishes nothing to the warm cache, so no later run replays it; while the panic reproduces, runs start from the last generation published before it, or cold when there is none. Only the per-file walk is isolated: a panic while parsing, building the project index, in the effect and throw fixpoints, or in `annotate`'s value margin still ends the run. `RUST_BACKTRACE=1` prints the full panic report for a bug report.
