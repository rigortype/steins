- **Declaration fatals now follow engine ancestors: `class Y implements Countable {}`, `class F extends FilterIterator {}`, `class E extends Exception { function getMessage() {} }` and `class C extends Closure {}` report `class.abstract-unimplemented`, `override.final` and `class.extends-final`, as their project-ancestor twins do (#939).** The ancestor is read off the analysing PHP's own reflection, so a run with no live PHP (`--no-php`), a PHP outside the declared target range or one with a runtime-redefinition extension, and a class the running PHP lacks all stay silent, as before. The engine's abstract methods and interface methods are requirements, a concrete engine method satisfies one, and the same walk now judges an engine final method overridden (`override.final`), an engine method made static or non-static (`override.static-mismatch`), a narrowed engine visibility (`override.visibility-weakened`) and a parameter-count incompatibility with an engine method (`override.parameter-variance`). A return type that differs from an engine tentative return type is a deprecation, not a fatal, so it is not reported and `override.return-variance` is never premised on it; engine parameter types are not compared, since reflection carries counts only. Implementing `Throwable`, `Traversable`, `DateTimeInterface` or `UnitEnum` directly, or `Iterator` together with `IteratorAggregate`, is declined as each is a different fatal. See ADR-0078's 2026-10-11 amendment.
