- **A write through another name for the same object no longer leaves Steins believing the old property value.** Objects are handles, so after `$arr = [$o]; foreach ($arr as $q) { $q->p = 'x'; }` the property `$o->p` is `'x'`. Steins dropped the write, because it could not tell which object `$q` held, and kept the old value of `$o->p`. A finding could then rest on that stale value. Now an object that reaches a name Steins cannot follow is marked as shared, and a write through such a name forgets the property values of every shared object. The routes include storing the object in an array, a `match` or a ternary, reading it back with `foreach`, `list()`, `current()`, `array_pop()` and similar functions, passing it to a callback, and a function that returns its argument. The writes include a property assignment, a method call, `unset()`, passing the property by reference, and passing the object to a function that changes it. An object that was never shared keeps its values. A loop now also applies to the code after it the forgetting that a call or write in its body caused, a `switch` that Steins does not analyze forgets the property values of shared objects, and a statement that contains `yield` forgets what the code that consumes the generator could change.
  - **Findings can disappear:** a finding that rested on a property value that a write through another name had replaced, such as an argument mismatch against the old value. None moved on the ten public corpus packages, at `strict` or at `default`. The `transform` dry-runs plan the same edits, and `effect-diff` reports no event.
