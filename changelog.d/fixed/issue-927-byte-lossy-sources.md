- **A source file that is not valid UTF-8 (a legacy Shift-JIS or EUC-JP file) no longer produces findings built on strings or names that its decoding made alike.** Steins reads such a file with every ill-formed byte replaced by U+FFFD, so two different strings such as `"\x82\xA0"` and `"\x82\xA2"` became the same text: `array.duplicate-key` fired on a map whose keys differ, `$a === $b` folded to `true`, `strlen($a)` folded to `6` and `count($map)` to `1`, and two properties named `$field\xC9` and `$field\xFF` were one property, so a `type.property-mismatch` stood on the wrong one. A string literal over such a byte is now the bytes the file spells, so it compares and keys by bytes and does not fold (the folds above now say `false`, `int<1, max>` and `2`, as PHP does). A file with a class, function, method, property, constant or variable name token over such a byte now makes no claim, and other files no longer descend into its function and method bodies. A string that merely contains such a byte does not take the file out of the analysis, even when it is a call argument or a callable name; it is just not read as a name. An effect label over such bytes is the one string read as a name that is not declined: it stays an unknown label, so `effect.unknown-label` and, under the strict profile, `effect.envelope-exceeded` still report on the declaration whether the file writes the byte raw (Latin-1) or as an escape (valid UTF-8), and the message spells the label with the escape PHP uses (`io\xC9`, where it printed a U+FFFD, and it no longer offers `io` as a did-you-mean for it). Findings only disappear, and only in files that are not valid UTF-8. In a valid UTF-8 file two texts change and no finding comes or goes: the effect-label message above, and the gap reason of a callable string over such bytes written as an escape (`array_map("\xC0", …)` now reads `no-effect-row` where it read `unresolved-callback`); the ten public corpora are all valid UTF-8 and report the same findings, byte for byte.
  - **`check --fix` and `transform` leave a file that is not valid UTF-8 alone,** with a notice that names it (`byte-lossy-source`), and still check and write the rest of the plan. `transform` counts each site in such a file as refused with that reason, so the enumerated/promoted/refused line, the refusals and the JSON oracle say what was written; `check --fix --format json` lists the files it left out under `fix.skipped`, and their findings stay with the `fix` payload that was not applied. They edit the replaced text, and writing it back would overwrite the file's own bytes with U+FFFD. Convert the file to UTF-8, or make the edit by hand. A `check --fix` whose every fix is in such files is refused with that reason, MCP `apply_plan` refuses a plan that edits one, and `annotate` refuses such a file, since its output is a copy of the text.
  - **Known costs.** A file with a name token over a replaced byte reports nothing, including true positives that need that file's bodies (for example a call into it with a proven `null`). A name inside a docblock is not yet read through the decode map, so a docblock class name over such a byte can still collapse (#983). The `array.duplicate-key` message for a byte key now prints the bytes the way PHP spells them (`"caf\xE9"` instead of `'caf�'`), so a baselined entry for such a key in a non-UTF-8 file can surface again once.
  - **A genuine U+FFFD in a valid UTF-8 file is untouched:** a duplicated `"\u{FFFD}"` key still reports, and two byte-identical Latin-1 keys still report. Moving the source text itself to bytes stays ADR-0080 section 3.2.
