- **A source file that is not valid UTF-8 (a legacy Shift-JIS or EUC-JP file) no longer produces findings built on strings or names that its decoding made alike.** Steins reads such a file with every ill-formed byte replaced by U+FFFD, so two different strings such as `"\x82\xA0"` and `"\x82\xA2"` became the same text: `array.duplicate-key` fired on a map whose keys differ, `$a === $b` folded to `true`, `strlen($a)` folded to `6` and `count($map)` to `1`, and two properties named `$field\xC9` and `$field\xFF` were one property, so a `type.property-mismatch` stood on the wrong one. A string literal over such a byte is now the bytes the file spells, so it compares and keys by bytes and does not fold (the folds above now say `false`, `int<1, max>` and `2`, as PHP does). A file with a class, function, method, property, constant or variable name over such a byte now makes no claim, and other files no longer descend into its function and method bodies. Findings only disappear, and only in files that are not valid UTF-8; the ten public corpora are all valid UTF-8 and report the same findings, byte for byte.
  - **`check --fix`, `transform`, MCP `apply_plan` and `annotate` refuse a file that is not valid UTF-8,** by name and before anything is written, because they edit the replaced text and writing it back would overwrite the file's own bytes with U+FFFD. Convert the file to UTF-8, or make the edit by hand. `transform` refuses at plan time, so a dry run does not show a diff that `--apply` would turn down.
  - **A genuine U+FFFD in a valid UTF-8 file is untouched:** a duplicated `"\u{FFFD}"` key still reports, and two byte-identical Latin-1 keys still report as `array key "caf\xE9" is declared twice`, now spelled the way PHP spells those bytes. Moving the source text itself to bytes stays ADR-0080 section 3.2.
