- **Appending to or writing into one array a few thousand times in straight-line code no longer takes minutes, and an array wider than 256 keys is summarized instead of listed.** Each `$a[] = v` and `$a['k'] = v` on an array whose keys the analysis had watched being built rebuilt the whole key list, and the rebuild itself was quadratic, so the cost of N such statements grew with N cubed: 3,000 appends took about 10 seconds and a generated file with tens of thousands never finished. The lookups inside the rebuild are now linear or logarithmic, and the 256-key width bound (ADR-0062 A-G6), until now enforced only for array literals, applies to every array shape the analysis builds or reads: appends, offset writes, `array_push` and `array_unshift`, joins of two shapes, and a docblock `array{…}` wider than 256 keys. Past 256 keys the shape keeps the key type and the value type but not the key list, so a proven `offset.undeclared` on a key of that key type can disappear: after 300 appends of `$a[] = …`, reading `$a[300]` or `$a[-1]` was reported and now is not, while reading `$a['k']` is still reported because the keys are known to be integers. The array is also no longer a witnessed list past that point, so `count()` widens to `int<1, max>` and `array_is_list` to `bool`. The degradation only widens; the public corpora report the same findings as before.
  - A write that adds a key (`$a[1000] = 'x'` on a list) no longer keeps the array's list verdict, which wrongly made the result a list. This was already the case for a declared `non-empty-list` and for a 300-entry literal; it could report `phpdoc.param-mismatch` or `phpdoc.return-mismatch` against an `associative-array` declaration and fold `array_is_list` to true.
