# なぜエフェクトなのか

[English](../why-effects.md)

> [!NOTE]
> この文章の内容は設計目標を含んでおり、2026-08-02時点では多くが未実装・未配線です。
> 正確な現状は[未実装項目](../type-specification/not-implemented.md)を参照してください。

Steinsは一つの問いから始まった。PHPの解析器は、メソッドがどんな値を返すかだけでなく、
そのメソッドを呼ぶと外の世界に何が起きるかを示せないだろうか。

この問いは、大規模なPHPアプリケーションで意味を持つ。コントローラのメソッド自身には
SQLもHTTPクライアントも時刻取得も出力処理も現れない。それでも、リポジトリ、
フレームワークの抽象、DIを経由した先ですべてに到達することがある。呼び出しを一つ
変えただけで、引数や戻り値の型を変えずにデータベース依存やネットワーク通信が加わる。
テストも通るかもしれない。しかし、そのメソッドが実行時に触れる範囲は変わっている。

Steinsは、この範囲を第二の推論次元である**エフェクト**として扱う。

## 二つの次元

型は、式が受け取る値と生成する値を表す。

```php
function findUser(UserId $id): User
```

このシグネチャからは、`findUser`がデータベースを読むのか、現在時刻を参照するのか、
HTTPリクエストを送るのか、何かを出力するのかは分からない。Steinsは、そうした作用に
階層的なラベルを付ける。

```text
io.db
io.net.http
nondet.time
output
```

Steinsはラベルを呼び出しグラフ上で伝播させる。コントローラがリポジトリを呼び、
その先でカタログ登録済みのデータベースプリミティブに到達すれば、データベースの
エフェクトはコントローラのエフェクト要約まで届く。コントローラ自身がデータベースを
直接参照している必要はない。

エフェクト要約は、メソッドから観測できる外界との接点を静的に記述する。変更前後の
要約を比較すれば、通常の型シグネチャが変わっていなくても、新しい依存を発見できる。

## 着想の源

[Flix](https://flix.dev/)は、エフェクトを型システムの一部にすることで、言語がどれほど
大きな力を得られるかを示した。中でも重要なのがエフェクト多相である。`map`のような
高階関数のエフェクトは、渡された関数のエフェクトに依存する。純粋なコールバックを
渡せば`map`も純粋なままであり、エフェクトを持つコールバックを渡せば、そのエフェクトが
呼び出しに加わる。Flixはほかにも、sub-effecting、effect exclusion、purity reflection、
代数的エフェクトハンドラを備えている。

PHPで直接のきっかけになったのは、
[PHPStanのpure/impureモデルとmap系関数の純粋性に関する検討](https://github.com/zonuexe/phpstan-notes/blob/master/generated-report/20260703-effect-system-design.md)
だった。平坦なpure/impureフラグの限界は、二つの例によく表れている。

- `array_map`が純粋かどうかは、渡されたコールバックによって変わる。
- `preg_match(..., $matches)`のようなby-reference出力引数はローカルな束縛を変更するが、
  呼び出し元から観測できるエフェクトを生まない場合がある。

PHPStanはすでに、この判断に使える情報の一部を持っている。しかし、真偽値の
`hasSideEffects`フラグでは関係全体を表せない。`array_map`をpureと宣言すれば、
エフェクトを持つコールバックに対して嘘になる。impureと宣言すれば、純粋なコールバックに
対して嘘になる。

Steinsは、PHPStanの後方互換性という制約を受けずに、より強いモデルを試す場所として
始まった。そして、そのモデルによって大規模なPHPコードの変更を、より信頼できるものに
できないかを探っている。

## Steinsのモデル

Steinsは外付けの静的解析器である。言語構文と、カタログ登録済みの組み込み関数・
拡張関数の呼び出しから原始的なエフェクトを見つけ、解決できたプロジェクト全体の
呼び出しグラフ上で不動点まで伝播させる。

エフェクトには階層的なドットパスラベルを使う。広いラベルは、その子孫を包摂する。

```text
io
└── io.net
    └── io.net.http
```

関数には、**エフェクトエンベロープ**と呼ぶ上限を宣言できる。

```php
#[\Steins\Pure]
function slug(string $value): string
{
    return strtolower(trim($value));
}

#[\Steins\Effect('io.db')]
function findUser(UserId $id): User
{
    // ...
}
```

この宣言がエフェクトを発生させたり処理したりするわけではない。Steinsに対して、
実装から証明されたエフェクトが宣言した上限に収まっているかを検査させる。

本体が見えるコールバックに、明示的なエフェクト変数は必要ない。call-site value
propagationによってコールバックを解析し、そのエフェクトを高階関数の呼び出しにjoin
できる。不透明なcallableについては、条件付き純度の契約で扱える場合がある。PHPに
effect row構文を追加せず、エフェクト多相の有用な一部を回収する設計である。

インターフェースのメソッドもエンベロープを持てる。DIによって具象実装への
呼び出しグラフが切れても、インターフェース越しの呼び出しにエフェクト情報を残せる。
実装は、インターフェースのエンベロープより広いエフェクトを持ってはならない。
これはエフェクトに対するリスコフの置換原則である。

## 通信手段の事実と意味の事実

低水準の解析は、HTTPリクエストという通信上の作用を特定できる。

```text
io.net.http
```

そのリクエストが何を意味するかについては、対象パッケージやプロジェクトがさらに多くの
知識を持つ。プラグインは、SendGridの呼び出しに意味上のラベルを追加できる。

```text
io.net.http
sendgrid.mail.send
email.send
```

これらのラベルは同時に存在する。`io.net.http`は通信手段を、
`sendgrid.mail.send`はプロバイダ上の操作を、`email.send`はアプリケーション上の
意味を記録する。複数の次元を一つの分類体系へ押し込めなくても、ポリシーごとに
異なる問いを立てられる。

同じ区別はデータベース接続にも当てはまる。PHP上ではどちらも`PDO`型であっても、
異なるデータベース系統や接続ロールを指すことがある。将来のprovenance対応ルールは、
接続ファクトリが返す値に次のようなラベルを付けられる。

```text
acme.db.catalog.connection.master
acme.db.catalog.connection.slave
```

そのreceiverに対してPDOの操作を呼んだとき、Steinsはreceiverのprovenanceを
エフェクトに変換できる。

```text
acme.db.catalog.master
```

接続経路とSQL操作は別々の事実である。master接続に`SELECT`を送れば、
master経路のエフェクトとクエリ操作の事実を両方持つ。この分離によって、
コントローラがどのデータベースへ到達するか、読み取り専用の処理がmaster接続へ
依存していないか、変更によって新しいデータベース経路が加わっていないかを確認できる。

## Steinsではないもの

Steinsは、PHPに代数的エフェクトを追加するものではない。

代数的エフェクトを持つ言語では、プログラムがエフェクトを実行するとハンドラへ
制御を移し、捕捉した計算を再開できる。この仕組みを使って、ユーザー定義の制御フロー、
例外、ジェネレータ、非同期実行、バックトラッキング、実行時の依存差し替えなどを
実装できる。

Steinsは次の機能を提供しない。

- `perform`、`handle`、`resume`に相当する構文
- 継続の捕捉や再開可能なエフェクトハンドラ
- ユーザー定義の制御フロー機構
- エフェクトの実行時差し替え、リダイレクト、記録、再生
- ハンドラによるDI
- エフェクト型に基づくコンパイラ最適化

Steinsは既存のPHPの振る舞いを観測するが、その実行を仲介しない。ラベルは呼び出しを
分類するものであり、ハンドラが解釈できる操作として具体化するものではない。

Steinsには明示的なeffect rowも、汎用的なエフェクト変数もない。プロジェクトまたは
宣言から十分な情報を得られる場所では、コールバックの伝播によってエフェクト多相に
相当する振る舞いを回収できる。しかし、一般的なrow-polymorphic type systemではない。

診断が出なかったからといって、純粋性が自動的に証明されたわけでもない。動的dispatch、
未解決の呼び出し、不完全な組み込みカタログ、伝播budgetによって、要約が非網羅的に
なることがある。Steinsはunknownをpureとして扱わず、「既知のエフェクトに加えて、
ほかにも存在する可能性がある」と記録する。エンベロープ診断が使うのは、証明された
エフェクトだけである。

## 提供したい価値

Steinsは、既存のPHPコードが持つエフェクトの範囲を観測可能にする。

- 各コントローラがデータベース、ネットワーク、時刻、出力、グローバル状態のどこへ
  到達するか
- 広いエフェクトの背後に、どの具象インフラ系統が存在するか
- リファクタリングでエフェクトが追加または削除されたか
- 実装が抽象側で宣言されたエンベロープを超えていないか
- エフェクトを持つオーケストレーションから、純粋な計算の核をどこで分離できるか

この範囲は、言語レベルの代数的エフェクトシステムより狭い。一方で、すでに存在する
PHPコードへ適用できる。正確なエフェクトの観測、unknownを隠さない姿勢、
プロジェクト固有の意味ラベルによって、大規模な変更をレビューしやすくし、安全に
リリースできるようにする。それがこのプロジェクトの賭けである。
