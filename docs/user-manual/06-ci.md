# CI integration

Running `steins check` in CI is not a special mode — it is the same command
you run at your terminal, pointed at the same tree, gated the same way any
other step is: a nonzero exit fails the job. This chapter covers what a CI
author needs beyond that: which exit code means what, how the baseline
ratchet behaves when nobody is sitting at a keyboard to answer prompts, how
findings become inline PR annotations and code-scanning alerts, and what
the PHP sidecar needs from the runner. Copy-pasteable workflow
files live in [`ci-templates/`](ci-templates/README.md), exercised end to
end against a real install for this chapter — every transcript below is
real output, not invented.

## The exit-code contract, as CI sees it

`steins check` has three exit codes, and CI treats none of them specially —
a nonzero exit fails the step the way any other tool's nonzero exit does.
What matters is that a CI author knows what each one is actually saying:

- **`0`** — nothing fail-level was displayed. A clean run, or a run where
  every surfaced finding was baselined or demoted to `warn`.
- **`1`** — at least one fail-level finding was displayed. Your code has a
  provable problem.
- **`2`** — usage or config error: an unknown flag, an unparseable
  `steins.toml`, an unknown profile, **or a path argument that does not
  exist**.

The third case is the one worth stopping on. Before the check landed
(ADR-0050 §7, ADR-0054 §10), an explicit path that named nothing —
`steins check src/Typo` after a rename, a stale path left in a workflow
file — fell through the file collector, found zero `.php` files, and
printed a clean empty report at exit `0`. A CI job stayed green after the
directory it was supposed to check stopped existing. That is a false
all-clear, and for a tool whose entire value proposition is "silence means
verified," a false all-clear is the one failure mode that cannot be
tolerated. Today the same typo is a hard error, checked before any
analysis runs and before any output is produced:

```
$ steins check ./src-typo
steins: path does not exist: ./src-typo
$ echo $?
2
```

Under `--format json` the same call emits **no document at all** — the
error line above on stderr, nothing on stdout — so a consumer that
naively parses stdout as JSON gets a parse failure instead of a
well-formed `{"findings": []}` it would read as clean.

The consequence for your workflow file is mostly what *not* to do: don't
wrap the check step in `continue-on-error: true`, don't pipe it through
`|| true` "to be safe," and don't special-case exit `2` as a flake to
retry. A GitHub Actions `run:` step already fails the job on any nonzero
exit with zero extra configuration — exit `1` and exit `2` both red the
build for free. The discipline this chapter asks of you is negative: leave
that default alone. Every deviation from it — swallowing the exit code,
grep-ing stdout for a specific string instead of trusting the code, a
custom wrapper script that maps unexpected codes to `0` — reopens exactly
the false-all-clear hole ADR-0050 §7 closed.

## Installing Steins in a CI job

[Installation and quickstart](01-installation-and-quickstart.md) covers all
four channels in full; this section only says which ones make sense in a
CI job and forward-links rather than repeating the details.

**Composer** is the default for a CI job the same way it is the default
for a project (ADR-0025's separation into a tooling package and an inert
attributes package is explained there). `composer require --dev
typedduck/steins` installs a small PHP shim that resolves the version from
`composer.lock` — so CI and every developer analyze with the exact same
build — and on first invocation downloads the matching release binary,
verifying it against the sha256 the release published. Later invocations
in the same job reuse the cached binary and touch the network not at all.
This is the channel [`github-actions.yml`](ci-templates/github-actions.yml)
uses.

**A prebuilt binary**, fetched directly from the
[releases page](https://github.com/rigortype/steins/releases) with its
own sha256 verification, suits a runner that should not carry PHP just to
install the analyzer, or a self-hosted runner where you already manage
binary caching yourself.

**Homebrew** (`brew install rigortype/tap/steins`) is the right choice for
a macOS runner that needs `steins` on `PATH` without a PHP prerequisite —
useful when the job's own PHP setup happens later, or not at all if you
run with `--no-php`.

Whichever channel you pick, pin it: Composer pins through `composer.lock`
automatically; the binary and Homebrew channels want an explicit version
in the download URL or formula rather than "always latest," for the same
reason you pin any other CI dependency — a silent version bump between
runs makes a red build impossible to bisect.

## The PHP sidecar on CI runners

Steins types literals by executing the project's own PHP over IPC (the
sidecar, ADR-0004) so a folded value reflects the runtime you actually
ship on, not a static emulation. In CI that means the job needs a `php`
on `PATH`, and it should be the version your project's `composer.json`
declares as its floor — the sidecar answers questions like "does this
extension export this function" and "what does this builtin return" for
*that* PHP, not an abstract one.

[`shivammathur/setup-php`](https://github.com/shivammathur/setup-php) is
the conventional Actions step for this — every workflow template in
`ci-templates/` uses it:

```yaml
- uses: shivammathur/setup-php@v2
  with:
    php-version: "8.3"
    coverage: none
```

`coverage: none` skips installing Xdebug/PCOV, which this job does not
need and which only slows setup down.

If a runner genuinely cannot carry PHP — a minimal container image, a
job that only lints — `--no-php` runs the **sound subset**: no false
positive is ever added, but findings that need the runtime to answer a
question widen away. Concretely, the whole absence family goes quiet
(`call.undefined-function`, `class.undefined`, and per ADR-0049 §1 A2
`call.undefined-method`, since ruling out a builtin/extension homonym
needs the sidecar), while value-precise mismatches that fold statically —
passing `null` where a declared `string` sits — still fire. That's a real
coverage cost, not a free lunch:

```
$ steins check --no-php .
note: running as sound subset (no PHP sidecar) — findings that require executing PHP are omitted, and builtin return types come from the catalog's declarations, unverified
./src/main.php:10:22: error[type.argument-mismatch]: argument null (from $name, assigned at line 8) to Greeter::greet() cannot become string $name — proven TypeError (strict mode)
$ echo $?
1
```

Decide per job: a fast lint-only job might accept the narrower surface for
speed; the job that actually gates merges should carry PHP.

## The baseline loop in CI

A CI check that fails on every pre-existing finding the day it is adopted
never gets adopted. [Profiles, baseline, and suppression](05-profiles-and-baseline.md)
covers the full ratchet workflow; here is the shape it takes specifically
in CI.

The baseline file is JSONL, keyed by content hash rather than line number
so it survives unrelated edits, and its **default path has a leading dot**:
`.steins-baseline.jsonl`. `check` looks for that exact filename with no
flag needed — commit it at the repo root and every `steins check .` in
every job picks it up automatically:

```
$ steins check --set-baseline .
steins: wrote 1 baseline entries to .steins-baseline.jsonl (profile `default`)
$ git add .steins-baseline.jsonl
```

```
$ steins check .
1 findings in baseline
$ echo $?
0
```

No `--baseline` flag appears in either invocation above — the leading-dot
name is discovered on its own, for both reading and writing. Once
`.steins-baseline.jsonl` sits in the repo, the CI loop is exactly: **new
findings fail the build, baselined findings do not.** A pull request that
introduces a new provable break shows it, unbaselined, on stdout, and the
job goes red. A pull request that only touches code with pre-existing
baselined findings stays green even though those findings still exist —
that debt was frozen deliberately, not fixed.

**`--set-baseline` is a command a human runs locally, never a step a CI
job runs.** There is no automated variant of this by design: a CI job
that ran `--set-baseline` on every push would rewrite the baseline to
match whatever the branch currently produces, which means a new bug
introduced and merged in the same push gets silently absorbed into the
baseline instead of failing the build — the ratchet turning into a rubber
stamp. The baseline shrinks only when a person runs `check --set-baseline`
after fixing findings, reviews the diff to `.steins-baseline.jsonl` like
any other change, and commits it. CI's only job with respect to the
baseline file is to read it, never to write it.

> **If you know PHPStan or Psalm:** this is the same discipline you
> already apply to `phpstan-baseline.neon` — regenerate it locally after a
> cleanup pass, commit the diff, never let a pipeline step regenerate it
> on your behalf. Steins has no CI-side equivalent of a "baseline refresh"
> job for the same reason PHPStan projects that run one regret it.

Raising the active profile past what the baseline was captured under
drowns loudly rather than silently — the run says exactly which ids are
now unbaselined, so a config change that widens the surface cannot
quietly slip past review the way a rewritten baseline could:

```
$ steins check --profile contracts .
./src/Invoice.php:14:9: error[throw.undeclared]: RuntimeException can escape Invoice::total() but is not declared (@throws LogicException) — proven escape
1 findings in baseline
active profile `contracts` surfaces 14 id(s) the baseline (captured under `default`) did not — those findings are unbaselined (rerun --set-baseline to capture them)
```

## Inline PR annotations and machine-readable output

`check` renders one displayed finding set in several spellings, and which
one you pick never changes what was found. `--format github` emits GitHub
Actions workflow commands, so findings land as inline annotations on the
pull request diff:

```
$ steins check --format github .
::error file=src/main.php,line=10,col=22,title=type.argument-mismatch::argument null (from $name, assigned at line 8) to Greeter::greet() cannot become string $name — proven TypeError (strict mode)
```

- Fail-level findings are `::error` (they red the job); a `warn`-demoted id
  from a user profile is `::warning` (annotated, exit-neutral); the debug
  lane's dumps are `::notice`. The command name and the exit code answer
  the same question, so they cannot disagree.
- `title=` carries the finding id, so an annotation is triageable from the
  PR diff view without opening the job log.
- GitHub's workflow-command escaping is applied for you, in both registers
  — `%`→`%25`, `\r`→`%0D`, `\n`→`%0A` in the message, and additionally
  `:`→`%3A`, `,`→`%2C` in `file`/`title`. A file path with a comma in it is
  the realistic case, and it is handled.

**You usually do not have to pass the flag.** With no `--format`, `check`
selects `github` when `GITHUB_ACTIONS=true` is in the environment — which
GitHub sets on every step — and `text` everywhere else. An explicit
`--format` always wins, so `--format json` in an Actions job still gets
JSON and `--format text` still gets the plain report. Detection changes
only the spelling: identical findings, identical exit code. Nothing else is
detected, deliberately: a generic `CI=true` does not name a rendering
anything can consume, and `text` is already correct there.

Paths pass through as given, so run `check` from the repo root with
relative paths — that is what GitHub matches annotations against.

`--format json` remains the surface for anything that is not GitHub. Each
finding carries `id`, `layer`, `level`, `path`, `line`, `column`, and
`message`, plus run-level `profile` and suppression counts — the same
fields [the CLI reference's `--format json` section](02-cli-reference.md#check)
documents in full.

`set -o pipefail` is load-bearing in any step that pipes `check` into
something else, and it is not boilerplate. Without it, a `check` that exits
`2` (the usage-error case from the first section) still lets the pipeline
report the last command's exit code — `0`, because `jq` on empty stdin runs
zero times and succeeds — and the step goes green on exactly the
false-all-clear ADR-0050 §7 exists to prevent. Verified both ways:

```
$ set -o pipefail
$ steins check --format json ./src-typo | jq -r '.findings[]'
steins: path does not exist: ./src-typo
$ echo $?
2
```

```
$ steins check --format json . | jq -r '.findings[]'
{
  "id": "type.argument-mismatch",
  "layer": "proof",
  "level": "fail",
  "path": "./src/main.php",
  "line": 10,
  "column": 22,
  "message": "argument null (from $name, assigned at line 8) to Greeter::greet() cannot become string $name — proven TypeError (strict mode)"
}
$ echo $?
1
```

> **If you know PHPStan or Psalm:** `--format github` is the equivalent of
> their GitHub error formatter, and it needs no action wrapper — the
> binary detects the runner and spells its own output.

## Uploading to code scanning with `--format sarif`

`--format sarif` writes a SARIF 2.1.0 log to stdout, which
`github/codeql-action/upload-sarif` ingests into the repository's Security
tab:

```yaml
      - name: steins check (sarif)
        continue-on-error: true
        run: vendor/bin/steins check --format sarif . > steins.sarif

      - uses: github/codeql-action/upload-sarif@v3
        with:
          sarif_file: steins.sarif
```

Two details are load-bearing:

- **`continue-on-error: true` on the check step, not a flag on Steins.**
  A run with findings exits `1`, and that is identity — "surfaced means
  fail". There is no `--exit-zero`, because a flag that makes `check`
  report success on a failing tree is a flag for turning the gate off. If
  you want the upload to happen *and* the job to red, let the check step
  continue on error and gate the job on a later step (or on the code
  scanning alerts themselves).
- **Run from the repo root with a relative path.** Paths pass through as
  given, and code scanning matches alerts to files by repo-root-relative
  path. Steins does not guess a repo root it was not shown.

Alert tracking across runs uses `partialFingerprints` — the same hash the
baseline uses to recognize a finding after unrelated edits — so an alert
stays one alert when the lines around it move. `run.automationDetails.id`
is `steins/<profile>`, so a `default` gate and a `contracts` debt dashboard
can upload in parallel as separate categories.

What the log deliberately does not contain is a `suppressions` section:
baselined and `@steins-ignore`d findings are counts in `run.properties` and
nothing more. Your baseline's contents are not published to the Security
tab, and the three suppression channels stay the whole suppression surface.

## `steins doctor` as a CI preflight

`doctor` reports posture and runs no checks; its exit is independent of
what `check` would find (ADR-0054 §8). Two of its three exit codes matter
for CI:

- **`0`** covers every posture doctor can report, degraded ones included —
  no PHP on `PATH` is a reported mode, not a failure, so `doctor`
  alone never fails a job just because a runner lacks PHP.
- **`1`** is a hard **configuration contradiction**: `steins.toml` fails
  to parse, an unresolvable profile, a baseline file whose header is not
  valid JSON. This is the case worth gating a preflight step on — it
  means `check` in the very same job is about to hit the identical
  problem, just later and with less context.

```
$ steins doctor
steins doctor — posture report (index-bound; runs no checks)
…
Config + active surface
  steins.toml: PARSE ERROR — steins.toml: parse error (TOML parse error at line 1, column 7
  |
1 | [check
  |       ^
invalid table header
expected `.`, `]`
)
  (configuration contradiction — doctor exits 1, ADR-0054 §10)
…
$ echo $?
1
```

A `doctor` step ahead of `check` catches this with a clearer message —
`check` would report the same parse error, but `doctor`'s report also
names the active profile, the coverage posture, and whether a committed
`.steins-baseline.jsonl` still matches the active surface, which is useful
context to have in the log regardless of whether the config is broken.
Adding the step costs one line:

```yaml
- run: vendor/bin/steins doctor
- run: vendor/bin/steins check .
```

Do not expect `doctor`'s exit to catch environment problems the way `1`
catches configuration ones — a missing PHP sidecar, a stale-but-dormant
baseline entry, a monkey-patching extension are all reported at exit `0`
on purpose (the lenient-default principle: a fact about the box is not a
failure the way an assertion your repo makes and the world refutes is).
If your team wants "no sidecar" to fail CI, that is a policy your
workflow enforces — checking `php --version` succeeded in the setup step,
say — not something `doctor` will fail on for you.
